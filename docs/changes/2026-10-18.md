# 2026-10-18 - Spyglass production vs `docs/actions.md`

Verified the generic Production rules and the Spyglass recipe in `docs/actions.md` against the code, then fixed the gaps.
Hammer and FishingPole are not documented in `actions.md`, so they were not judged.

## What matched the docs (no change)

- Initiation creates the unfinished item in the room and locks the starting item.
- Stage order and room requirements for the Spyglass (Workshop, Forecastle, Workshop).
- Cost of specialized TP: 1 for the specialist, 2 for the Quartermaster, 3 for everyone else.
- Cancellation releases the locked items into the room and loses the invested TP.
- Completion gives the finished item to the player who provided the last TP.

## Gaps found and fixed

1. **Stage 2 was missing Sentry TP.** The docs ask for Scholar TP and Sentry TP; the code only handled Scholar.
2. **Insufficient TP was not guarded.** `ProductionItemBase.Contribute` only checked `ActionPoints - 1 == -1`, so a player paying 2 or 3 could go negative.

## Actions taken

- `StageContributionBase`: added `ContributionRoles`, `IsQuotaOpen(role)`, `WithContribution(role)` and `CalculateCostForContribution(player, quotaRole)`. `IsStageEnded` is now virtual and `IsProductionComplete` is derived from it.
- `ProductionItemBase`: added `Contribute(player, quotaRole)`. It rejects a closed quota and throws when `ActionPoints < cost`, before any points are spent. `Contribute(player)` keeps working and uses the stage's main role.
- `SpyglassSecondStageContributionData`: added the Sentry quota (`SentryContributions`, limit 8). The stage ends only when both quotas are full.
- `SpyglassContribution` is now an `ActionWithTargetsAvailability` (`ActionWithTargetsBase`) with two prompts, replacing the first version that used two instant actions (`SpyglassSentryContribution` was removed again):
  - Prompt 1: which unfinished spyglass of the room (`TargetSelectionPrompt.FromItems`, now with an optional description).
  - Prompt 2: which TP quota. Only open quotas are offered (Engineer in stages 1 and 3; Scholar and Sentry in stage 2, a full one is omitted).
  - Requirements come from the stage (room, item in room, quota open, TP for the cheapest open quota). `Contribute` re-checks the exact cost and quota for the chosen target.
  - Execution resolves the spyglass by target id and the quota from the target value (`ActionTargetsList.At(index)`).
- Tests:
  - New unit tests: `tests/Unit/Features/Actions/Productions/SpyglassProductionTest.cs` (22 cases, including the prompts of the availability).
  - Integration tests in `SpyglassProductionContributionAppTest`: now contribute through the prompts like a client does, plus new cases (quota prompt per stage, not-offered quota rejected, insufficient TP rejected).
- Results: integration 63/63 pass. Unit 155/165 pass; the 10 failures are the existing `RoomFactoryTest` adjacency cases that fail on `main`.

## Assumptions not covered by the docs

- **TP quotas are guesses.** The docs only say "high" and "very high". The numbers are assumed constants:
  - Stage 1: 8 (Engineer)
  - Stage 2: 12 Scholar ("very high"), 8 Sentry ("high")
  - Stage 3: 15 (Engineer)
  - "High" is already inconsistent between stage 1/2 (8) and stage 3 (15).
- **Stage 2 needs both quotas, in any order.** The docs do not say whether the Scholar and Sentry parts are independent or ordered.
- **Non-specialists choose which quota to pay.** Modelled as one action with a quota prompt (first built as two separate instant actions, then changed on request). A player pays 3 TP (2 for the Quartermaster) toward whichever quota they pick.
- **One contribution is always one unit of progress.** A non-specialist pays 3 TP for 1 unit of progress; the docs' "cost is tripled" was read that way.
- **Contribution is all-or-nothing.** A player with fewer TP than the cost is rejected; there is no partial contribution.
- **A full quota rejects further TP.** No overflow is carried to the next stage.
- **Several unfinished spyglasses in one room:** the player now picks which one by id. The action-level requirements (room, TP cost) are computed from the first spyglass of the room, while the prompts list all of them; `Contribute` rejects a quota the picked spyglass does not accept. Completion still removes the finished-from-room item by type (unchanged).

## Follow-ups

- The frontend (`NorthwestReactV2`) must handle `SpyglassContribution` as an action with targets (two prompts); regenerate the orval client.
- Hammer and FishingPole contributions stay instant actions: they have a single quota, so a quota prompt would be meaningless.
